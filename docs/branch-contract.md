# A branch of The Bounded Observer

A branch starts with a concrete subject and question. It identifies the information and operations needed to answer that question, selects the applicable mathematical model, and states how the model meets the subject.

## The operational contract

| Item | What the branch states |
| --- | --- |
| Question | The reading, prediction or action the branch aims to support |
| Record | Raw quantities, labels, missing information, units and provenance |
| Normalization | The reference or total used for bounded readings; “not applicable” where the record is not a normalized positive model |
| Readings | What can actually be measured, and by which observation convention |
| Operations | Allowed interventions, updates, conditioning and discarded information |
| Retained state | When two records are equivalent for the declared future operation class |
| Composition | How parts or updates combine, with the premises needed for that rule |
| Clock and resources | Physical time, sampling order or refinement index; integrated exposure where boundary claims use it |
| Bridge | What identifies mathematical variables with the subject; “pure mathematics” where no physical identification is made |
| Result | A scoped derivation, implementation or prediction with its evidence |
| Test and revision | Comparator, held-out outcome, failure condition and dated result |
| Source and home | Authoritative version, reproducible materials, licences and component repository if needed |

An item may be explicitly open. An unfilled physical bridge makes the connection a proposed extension. It does not erase a valid mathematical result inside the stated model.

## Separate role from status

Foundation, specialization, instrument, empirical test and historical source are different roles. Proof status, numerical checks, software verification and empirical outcomes are separate evidence fields.

- **[P]**: a proof under named premises, or a checked classical theorem.
- **[D]**: a proposed derivation awaiting the stated checks.
- **[H]**: a hypothesis with a defined test and loss condition.
- **Empirical status**: untested, supported in a specified comparison, failed, mixed or not applicable.
- **Implementation status**: proposed, prototype, tested in a specified setting or independently maintained.

A finite numerical check can find an algebraic error and support a proof's verification. It cannot establish an unrestricted theorem. A software test cannot establish physiological usefulness. Publication alone does not establish a successful prediction.

## Admit an extension

Use an existing branch when the question, operations and evidence belong to it. Add a branch when it introduces a distinct operational problem. Start its source and landing page here; use a component repository only for an independently maintained application, separate release lifecycle or large data workflow.

A registry entry needs a stable identifier, its contract, dependency sources, current evidence, next discriminating task and a dated authority. A new relation between branches needs its own reason: shared method, model specialization, measurement bridge, use of an instrument or an empirical transfer claim.

Preserve the original claim and record its correction or replacement. A failed candidate remains part of the branch's evidence even when a later candidate succeeds.
